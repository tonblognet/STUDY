# Самопроверка безопасности слоя 04

Проверка выполнена исполнителем отдельно от реализации. Она не является
независимым одобрением второго разработчика и не заменяет penetration test.

## Повторная самопроверка — 10 ноября 2026

В текущем слое устранены два подтверждённых дефекта сохранности и полноты:

- Миграция сохраняла `EducationProgram.slug`, а POST/import — public `id`.
  Для МАИ это разные строки: `mai-applied-math` / `mai-ami`. Новые записи
  используют slug, существующие строки обоих видов переиспользуются под
  блокировкой владельца. Заметки, история, версии и уже существующие дубли
  не переписываются и не удаляются. Если оба исторических ключа уже заняты,
  предпочтение canonical slug детерминировано; UI не приписывает неоднозначный
  ключ другой программе. Объединение прежних дублей автоматически не выполняется.
- Создание напоминаний исключает уже сохранённые ID до `LIMIT 200`, чтобы
  legacy-владельцы с более чем 200 строками получали последующие порции.
  Один запрос создаёт не более 200 уведомлений, видимый feed ограничен 100.
  SQL SHA-256 использует ту же UTC-строку с миллисекундами, что прежний Node.js
  код, без установки расширений PostgreSQL. Параметры передаются через Prisma.

Свежая проверка этой редакции: все семь обязательных gates по порядку;
1 457 unit/component-тестов в 43 файлах, 55 интеграционных проверок
(17 SSR + 1 миграция + 11 каталог + 26 account), без пропусков;
известных production-уязвимостей зависимостей не обнаружено. В account suite
воспроизведены переиспользование обоих ключей с сохранением всех полей,
одновременные POST/import, сохранение уже существующих дублей, backlog из
401 записи, отключённые напоминания и отзыв сессии между порциями.
SQL ID для всех 401 уведомления совпали с прежним JavaScript-хешированием;
legacy slug разрешается в подпись МАИ, личные заметки в уведомления не попадают.

Браузерная приёмка этой сборки фиксируется отдельно в handoff. Тесты используют
изолированные локальные PostgreSQL-схемы и SMTP. Production SMTP, внешний
penetration test, юридическая приёмка и независимый reviewer этим результатом
не подменяются. Найденные ранее риски checkout/webhook/support остаются
за слоем 06; он не начат до merge 04.

## Разграничение доступа — слой 04, 3 ноября

Сессия проверяется по хешу cookie, сроку, `revokedAt` и совпадению
`Session.authVersion` с `User.authVersion`. Новый login сохраняет текущую версию
при выдаче токена. Существующие сессии при миграции получают ту же начальную
версию `0`, что и их владельцы. Данные из уже выданного ответа отозвать нельзя;
новые запросы старым cookie отклоняются. Записи, ожидающие блокировку User,
повторно проверяют сессию под этой блокировкой до изменения данных. К ним
относится и генерация личных напоминаний из GET. Одиночный выход без действующей
сессии очищает cookie без мутаций БД. Массовый выход, сброс пароля и смена 2FA
отзывают сессии и challenges только владельца в одной транзакции.

`x-account-id` проверяет согласованность вкладки, но не заменяет cookie и не
выбирает владельца. Субъект операции и фильтры владельца берутся с сервера.
Чужой и отсутствующий корректный ID дают одинаковые статус и тело. Для
регистрации и восстановления сессия ещё не существует: права дают пароль,
одноразовый токен или код в зависимости от операции. Подтверждение email
требует ссылку и текущий пароль. Если кто-то заранее зарегистрировал чужой
адрес, владелец почты сначала задаёт свой пароль через восстановление и затем
подтверждает адрес. Публичные почтовые запросы дают нейтральный `202` до
поиска аккаунта и SMTP через Next `after`. Это принятие запроса, не подтверждение
доставки и не долговечная очередь. Ошибки логируются по виду операции без
адресов, паролей и токенов. Rate limit и Origin проверяются до планирования.

## Ранее выполненные проверки и самопроверки

Дополнение 2 ноября: одиночный отзыв приведён к User → Session → AuditLog,
как массовый отзыв; добавлена управляемая PostgreSQL-регрессия. Исправлен
перенос `DOCUMENTS_READY` в `documentsReady`, SQL-регрессия включена в integration.
Новые DB-регрессии пока не пройдены: Windows sandbox блокирует старт тестовой БД.
Подробности: [LAYER_04_RECOVERY_2026-11-02.md](LAYER_04_RECOVERY_2026-11-02.md).

Проверенные границы:

- Все account API извлекают владельца из серверной сессии. Мутации проверяют
  Origin и x-account-id текущей вкладки. Этот заголовок не авторизует запрос:
  несовпадение с владельцем сессии останавливает старую вкладку после смены
  аккаунта. Идентификаторы чужих записей не дают доступ к трекеру и уведомлениям.
- Пароли bcrypt cost 12; новые значения ограничены 72 UTF-8 байтами. Токены
  криптографически случайные, в БД только SHA-256. Email-коды: randomInt, nonce,
  HMAC-SHA256, TTL и пять попыток под блокировкой строки пользователя.
- Подтверждение email, сброс и потребление кодов выдержали конкурентные запросы:
  только один успешен. Просроченные ссылки, код и сессия отклонены. Повторная
  отправка инвалидирует предыдущую ссылку; настройка 2FA требует пароль и код
  отдельного назначения. Повторное использование кода другого действия запрещено.
- authVersion закрывает выдачу сессии по результату аутентификации, которая
  завершилась до отзыва доступа. Сброс и массовый logout инвалидируют сессии и
  challenges в одной транзакции. Проверены два токена одного пользователя.
- Лимиты атомарны между процессами, используют время PostgreSQL и хеш ключа;
  конкурентные 10 запросов дают ровно 5 разрешений при лимите 5. Сбой БД закрывает
  лимит. Поддельные forwarded headers игнорируются при TRUST_PROXY=false.
- Размер JSON ограничивается при чтении stream, независимо от Content-Length.
  Zod ограничивает значения и количество элементов; Prisma параметризует SQL.
- Состояние имеет версию, устаревшая запись получает 409. Локальные данные
  аккаунта не сохраняются в общем guest storage. Перенос гостевых данных и старого
  трекера требует явного действия; старый трекер дополнительно подтверждает владельца.
- Сохранённые отсутствующие программы удерживаются отдельно в прежнем списке
  владельца. Допуск вычисляется внутри блокировки вместе с проверкой версии;
  новый неизвестный ID, ID другого владельца и повторное добавление после удаления
  не получают исключения. Гостевой перенос не изменяет локальную копию: её очистка
  требует отдельного явного действия. Это исключает автоматическое удаление
  неподтверждённой записи другой вкладки между отдельными чтениями localStorage.
- Оба logout API проверяют x-account-id до отзыва сессий и очистки cookie.
  Несовпадающий или отсутствующий заголовок при активной сессии получает 409.
- Cookies HttpOnly/Secure/SameSite=Lax, ответы API private/no-store, Referrer-Policy
  no-referrer. Подтверждение email требует отправки формы, чтобы просмотр ссылки
  почтовым сканером не потреблял токен. После auth-переходов полный reload очищает
  клиентское состояние. Ошибки SMTP не изображают успешную доставку.
- Аудит содержит тип действия, владельца, сущность и агрегированные счётчики.
  Пароли, токены, коды, баллы и личные заметки в журнал не записываются.

Остаточные эксплуатационные ограничения: email-код зависит от безопасности
почтового ящика и не заменяет WebAuthn. Нужны HTTPS, доверенный reverse proxy,
SMTP, ротация AUTH_SECRET, резервные копии и очистка просроченных buckets/tokens.
Без прокси неизвестные IP разделяют консервативный общий лимит. Доставка писем
проверена на локальном SMTP, а не на production-почтовом провайдере. Эти настройки
и независимое ревью остаются условиями выпуска; production deployment не выполнялся.
