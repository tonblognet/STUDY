# Аккаунт и трекер — слой 04

## Контракт хранения

Избранное, сравнение и до восьми профилей ЕГЭ сохраняются в PostgreSQL в
UserStateSnapshot. GET возвращает version; PUT требует эту версию. Конкурентная
запись со старой версией получает 409, без перезаписи данных другой вкладки.
Клиент сохраняет несохранённые изменения только в памяти текущей вкладки:
данные аккаунта никогда не записываются в общее гостевое localStorage.
После конфликта пользователь явно загружает серверную версию. Снятая с каталога
программа остаётся в прежнем списке пользователя до явного удаления. Проверка
прежнего снимка и версии выполняется под одной блокировкой; новые неизвестные
ID и перенос отсутствующего ID в другой список не разрешаются.
Гостевые данные копируются только по кнопке владельца. После ответа сервера
локальная копия сохраняется целиком: localStorage не даёт атомарной проверки
изменений другой вкладки перед очисткой. Полный и частичный перенос различаются
по подтверждённым ID и полным профилям. Записи сверх лимитов, неизвестные программы
и отличающиеся профили не объявляются перенесёнными. Удалить локальную копию можно
отдельной явной кнопкой владельца.

Трекер хранится отдельно от избранного в AccountTrackerItem: удаление избранного
не удаляет заявление. Уникальность — владелец, публичный ключ программы и год.
Редактирование требует версии записи; история хранит последние 100 изменений.
Публичный ключ не имеет каскадного удаления при изменении каталога. Старые записи
серверного AdmissionTrackerItem перенесены миграцией через slug программы.
Явный старый DOCUMENTS_READY сохраняет отметку готовности документов;
из остальных статусов эта отметка не выводится. Исходная таблица сохраняется:
старые произвольные поля остаются в ней, новая модель их не интерпретирует.
Старое browser-only localStorage трекера не импортируется автоматически, поскольку
оно не содержит владельца. Кабинет предлагает явный перенос с подтверждением
«Это мои данные» и выбором года. Серверные записи не перезаписываются; локальная
копия остаётся после импорта, повторный перенос не создаёт дублей. Удаление копии
выполняется отдельной явной кнопкой. Неизвестные программы оставляют копию нетронутой.

## Безопасность

Одноразовые ссылки подтверждения и сброса хранятся хешированными; новый запрос
аннулирует предыдущую ссылку того же вида. Для подтверждения нужны ссылка из
почты и текущий пароль. Владелец почты может задать свой пароль через
восстановление доступа и затем вернуться к ссылке подтверждения. Неверный пароль
не расходует ссылку. При подтверждении после bcrypt сервер сверяет актуальный
хеш под блокировкой владельца и там же расходует ссылку. Пароль хранится bcrypt
cost 12. Новые пароли ограничены 72 байтами, чтобы исключить молчаливое усечение.
Код email имеет TTL 10 минут, максимум пять попыток, отдельный nonce и HMAC с
AUTH_SECRET; одинаковые шестизначные коды разных пользователей не конфликтуют.
Изменение двухэтапного входа требует пароль и отдельный email-код назначения.
Email-код — дополнительный шаг; это не фишингостойкий фактор WebAuthn/TOTP.

Сессии имеют непрозрачный токен, в БД хранится хеш; cookie HttpOnly, SameSite=Lax,
Secure в production. Смена пароля, двухэтапного входа и отзыв всех сессий увеличивают
authVersion, отзывают сессии и незавершённые challenges. Проверка версии при выдаче
сессии закрывает гонку с уже проверенными, но отозванными учётными данными.

RateLimitBucket использует атомарный PostgreSQL upsert и время БД. При сбое БД
лимит закрывает вход. Ключи хешируются. TRUST_PROXY=false объединяет неизвестные
IP в общий безопасный лимит; перед эксплуатацией доверенный прокси должен заменять
forwarding headers и только тогда допускается TRUST_PROXY=true. Вход ограничен
также по email. Периодически удаляйте просроченные RateLimitBucket и auth-токены
по эксплуатационному регламенту слоя 07; локального fallback нет.

Все мутации проверяют Origin и владельца из серверной сессии; userId тела запроса
не принимается. Оба варианта выхода проверяют x-account-id открытой вкладки:
старая вкладка не может завершить сессии другого аккаунта после смены cookie.
Чувствительные действия и изменения трекера журналируются без
паролей, кодов, токенов, баллов и текста заметок. Уведомления о смене настроек
безопасности сохраняются независимо от настройки личных сроков.

## Уведомления и внешние зависимости

Личные даты задаёт пользователь; это не подтверждённые сроки приёма.
Напоминания появляются в кабинете за 7 дней до даты и после неё, кроме завершённых
и отозванных заявлений. Проверка выполняется при открытии кабинета, сохранении
трекера и раз в минуту открытого кабинета. Дедупликация по пользователю, записи и
дате. Это не фоновая email-рассылка. Настройка in-app и прочтение сохраняются в БД.

Для реальных писем необходимы SMTP_URL, EMAIL_FROM и APP_URL; для кодов — случайный
AUTH_SECRET не короче 32 символов. Без SMTP отправка завершается ошибкой, успех не
имитируется. Тесты принимают письма только на loopback, без внешней доставки.
Production provisioning, резервные копии, SMTP deliverability и фоновый scheduler
относятся к слою 07. Платежи, AI и новые факты о приёме в слой не входят.
