# Публикация каталога

## Первоначальная настройка

1. Настроить `DATABASE_URL`, `CATALOG_STORAGE=database`, применить `pnpm db:migrate`.
2. Для локальной разработки создать редактора через `pnpm db:seed`, указав
   `SEED_ADMIN_EMAIL` и сильный `SEED_ADMIN_PASSWORD`. Development seed запрещён
   в production. В production использовать существующего уполномоченного редактора.
3. Проверить входные данные: `pnpm data:import -- --dry-run`.
4. Создать черновик:

```bash
pnpm data:import -- --actor=editor@example.ru
```

5. Войти в `/admin/catalog`, открыть версию, изучить изменения и источники.
   Ввести обоснование и подтвердить публикацию. До первой публикации каталог
   в режиме БД недоступен; административная очередь доступна редактору.

## Изменение опубликованных данных

В `/admin` открыть программу, исправить стоимость или места, сохранив точный
официальный URL, год, раздел документа, даты получения и проверки. Пустое
числовое поле означает `null`. Только verified публикуется как подтверждённое
число. Значения pending_review/conflicting_sources остаются в provenance и
не используются как подтверждённые показатели.

Сохранение создаёт черновик; следующий экран показывает diff. Публикация —
отдельное действие с подтверждением. Роли USER и SUPPORT не имеют доступа.

Опубликованные `id` и `slug` программы образуют постоянную пару: ID используется
избранным и сравнением, slug — ссылками. Импорт не разрешает заменять или повторно
использовать их, даже после снятия программы с публикации. Для восстановления
верните исходную пару; переименование заголовка не требует смены идентификаторов.
Перенос идентичности требует отдельной миграции пользовательских ссылок.

Для остальных полей или пакетных изменений:

```bash
pnpm data:export -- --output=tmp/catalog-candidate.json
# Отредактировать snapshot, сохранив baseRevisionId и provenance.
pnpm data:import -- --input=tmp/catalog-candidate.json --dry-run
pnpm data:diff -- --input=tmp/catalog-candidate.json
pnpm data:import -- --input=tmp/catalog-candidate.json --actor=editor@example.ru
```

`--university=mgu` применяет только записи этого вуза к текущей опубликованной
версии, сохраняя правки остальных. Для импорта из файлов репозитория после
первой публикации требуется `--base=ID_ТЕКУЩЕЙ_ВЕРСИИ`; это явное указание
основы, не автоматическое разрешение перезаписать правки. Изучите diff.

Если другой редактор уже опубликовал новую версию, старый черновик блокируется.
Повторите экспорт и перенесите только нужные изменения. Не меняйте ID основы
в старом файле, не сравнив его с актуальной публикацией.

## Откат и диагностика

Для возврата значения экспортировать текущую версию, перенести нужный факт
из предыдущей версии вместе с источником, импортировать и одобрить новый
черновик с причиной отката. Прошлые публикации не переписываются.

`/api/programs` возвращает `revisionId` и `publishedAt`; `/admin/catalog`
показывает текущую версию и историю. При сбое БД сайт не подставляет статические
сведения. Сначала восстановить доступ к БД, затем проверить `/api/health`
и соответствие версии в API и очереди публикаций.

## Интеграционные проверки

Создать отдельную PostgreSQL БД, имя которой заканчивается на `_test`, и задать
`TEST_DATABASE_URL`. Тесты сами применяют миграции к случайной схеме и удаляют
только её после выполнения. `DATABASE_URL` приложения не используется тестами.

```bash
pnpm test:catalog:db
pnpm build
pnpm test:integration
```

Последняя команда проверяет HTML в режиме снимка, затем запускает PostgreSQL-
сценарии и отдельный production HTTP-сервер в режиме БД. CI предоставляет
PostgreSQL 16 service. Обход проверки отсутствующей тестовой БД не предусмотрен.

Текущая версия не создаёт worker для периодического извлечения, не подтверждает
юридический статус вузов и не заполняет отсутствующие данные автоматически.
