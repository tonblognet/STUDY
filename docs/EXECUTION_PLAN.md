## Слой 00 — rebuild baseline

В baseline входит весь уже сделанный проект: визуальная система, страницы программ и вузов, каталог Москвы, логотипы, подбор по ЕГЭ, расширенные фильтры, сравнение, FAQ, поддержка, аккаунт, трекер, административная очередь, источники данных и тестовая база.

Критерии готовности:

- весь текущий проект зафиксирован одним стартовым коммитом;
- документация совместной работы и проектные Codex-навыки находятся в репозитории;
- все quality gates проходят;
- ветка опубликована в GitHub и становится основой `main`;
- оба разработчика могут воспроизвести запуск по `README.md` и настройку Codex по `docs/CODEX_SETUP.md`.

## Слой 01 — data foundation

Результат: данные пригодны для пользовательских решений и сопровождаются происхождением.

- Нормализовать сущности вузов, кампусов, программ, направлений, форм обучения, наборов ЕГЭ, контрольных цифр, стоимости и проходных баллов по годам.
- Разделить подтверждённые, устаревшие, ожидающие проверки и отсутствующие значения.
- Довести адаптеры официальных источников, дедупликацию, отчёт качества и админскую очередь проверки.
- Хранить URL источника, дату проверки, учебный год и тип источника для каждого чувствительного факта.
- Добавить подтверждённые московские вузы и программы; логотипы брать только с официальных ресурсов или хранить локальную разрешённую копию с указанием источника.

Готово, когда повторный импорт идемпотентен, отчёт качества не содержит необъяснённых критических ошибок, а UI не маскирует неизвестные значения.

## Слой 02 — admission engine

Результат: абитуриент вводит предметы и баллы и получает объяснимый список подходящих программ.

- Поддержать обязательные предметы, предметы по выбору, индивидуальные достижения и минимальные пороги.
- Добавить фильтры: вуз, направление, форма, бюджет/платно, стоимость, общежитие, военный учебный центр, аккредитация и качество данных.
- Разделить юридическую допустимость подачи и оценочную вероятность поступления.
- Показывать причину включения/исключения и недостающие данные.
- Покрыть граничные комбинации unit-тестами и сценариями интеграции.

## Слой 03 — public product

Результат: все публичные страницы ощущаются одной законченной системой.

- Унифицировать типографику, сетку, карточки, состояния загрузки/ошибки/пустого результата.
- Доработать каталог программ, каталог вузов, детали, сравнение и подбор на desktop/mobile.
- Добавить сохранение фильтров и понятные переходы между исследованием, сравнением и решением.
- Провести проверку доступности, клавиатурной навигации, контраста и производительности.

## Слой 04 — account and tracker

Результат: пользователь безопасно хранит личный набор программ и управляет поступлением.

- Завершить email verification, восстановление пароля, 2FA, отзыв сессий и rate limiting.
- Перенести критичное пользовательское состояние из локального режима в надёжное хранилище.
- Довести избранное, сравнение, профили ЕГЭ, статусы заявлений, дедлайны и уведомления.
- Проверить разграничение доступа и журналирование чувствительных действий.

## Слой 05 — AI guidance

Результат: AI помогает принимать решение, но не создаёт факты о приёме.

- Генерировать рекомендации только поверх подтверждённых данных и явно отделять факты от интерпретации.
- Добавить объяснение рекомендаций, ссылки на источники, отказ при нехватке данных и пользовательскую обратную связь.
- Создать eval-набор для точности, полноты, отказов и отсутствия галлюцинаций.
- Ввести лимиты, наблюдаемость, защиту персональных данных и контроль стоимости.

## Слой 06 — support, billing and admin

Результат: поддержка и платные функции управляются безопасно и прозрачно.

- Довести тикеты поддержки, SLA-статусы и пользовательскую историю обращений.
- Завершить платежный контур, идемпотентные webhook, сверку состояний и возвраты.
- Разделить роли администратора, контент-редактора и поддержки.
- Добавить аудит изменений данных и операционные инструкции.

## Слой 07 — production

Результат: систему можно безопасно выпустить и поддерживать.

- Настроить staging/production, миграции, резервные копии и процедуру восстановления.
- Добавить structured logs, health checks, error tracking, метрики и алерты.
- Выполнить security review, dependency review, нагрузочную и accessibility-проверку.
- Зафиксировать release checklist, rollback и ответственных.

## Эстафета между двумя разработчиками

Для нечётных слоёв первый разработчик реализует, второй ревьюит; для чётных — наоборот. Слой 00 завершает владелец текущего рабочего дерева, друг выступает первым независимым ревьюером.

1. Исполнитель обновляет `main`, создаёт ветку слоя и заполняет GitHub Issue из шаблона.
2. Исполнитель реализует только критерии текущего слоя и постоянно держит тесты зелёными.
3. Исполнитель обновляет `docs/HANDOFF.md`, отправляет ветку и открывает PR.
4. Ревьюер сначала воспроизводит проверки, затем проверяет архитектуру, UX, данные и безопасность.
5. Исполнитель исправляет замечания в той же ветке; новый слой не создаётся.
6. После одобрения PR сливается squash-merge в `main`, ветка удаляется.
7. Следующий исполнитель делает `git pull --ff-only origin main` и начинает следующий слой.

## Обязательный Definition of Done

Каждый слой обязан иметь законченное пользовательское или инфраструктурное назначение, тесты, зелёный CI, актуальную документацию, заполненный handoff и ревью согласно решениям владельца выше. Для UI обязательна проверка desktop/mobile; для данных — официальный источник; для auth/payments — отдельная security-проверка.
