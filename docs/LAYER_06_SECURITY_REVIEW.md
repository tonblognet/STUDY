User id из заголовка проверяет актуальность вкладки, но не авторизует её.

увеличивает authVersion, отзывает target sessions/challenges и записывает
только старую/новую роль. Данные профиля, почта и session/challenge IDs не
выгружаются через staff directory.

## Сохранность платежей

Все обработчики банковских результатов получают User owner lock до Payment
lock. Команды сотрудников блокируют actor и owner в порядке ID. Это сохраняет
порядок с account/session writers и FK-проверками при создании подписки.
Внешний HTTP выполняется после сохранённого claim, вне DB-транзакции.

Ключ checkout не переиспользует чужой заказ или другую программу тарифа.
Первый заказ фиксирует сумму, валюту, название/код, срок, entitlements,
терминал и окружение. Изменение Product не меняет старые условия.
UNKNOWN/истёкший lease не становятся основанием для второго Init. У Payment
одна INIT-попытка; READY URL сохраняется и выдаётся только из проверенной
незавершённой попытки без needsReview. Повтор после reload и возобновление
через историю используют тот же банковский заказ.

Только CONFIRMED создаёт grant. PK PaymentGrant.paymentId и уникальная связь
с подпиской дополняют блокировку; grant/подписка/финансовое состояние/аудит
сохраняются одной транзакцией. Пять параллельных уведомлений не удваивают
выдачу; отказ audit полностью откатывает мутацию. Поздний отказ не переводит
SUCCEEDED в FAILED, возвраты поглощают поздние подтверждения. Неожиданный
второй подтверждённый платёж при уже активном сроке отмечается для сверки,
вторая выдача не создаётся. HTTP-регрессия также воспроизводит позднее
подтверждение старого failed-заказа после нового успешного: повторная сверка
сохраняет needsReview, если подтверждённое списание осталось без grant.

Полный Cancel требует отдельного подтверждения суммы в UI, постоянного
внешнего ключа и роли. Потеря ответа не изображается возвратом. Повтор
неизвестного результата использует ту же операцию; проверен один внешний
возврат и один отзыв grant. Новый caller key не обходит уже существующую
попытку. Частичные события не складывают Amount и требуют ручной сверки.
Остальные платежи пользователя не отзываются.

Получение прав фильтрует live/SUCCEEDED, неотозванный grant, ACTIVE и срок
подписки; произвольное имя тарифа, ссылка success или sandbox этого не дают.
Исторические строки без снимка остаются неизвестными и не получают доступ
через сегодняшние параметры Product.

## Внешние данные и ошибки

API банка ограничен точными HTTPS-хостами и `/v2`, без URL credentials и
перенаправлений; body ответа ограничен 64 КБ, timeout — 10 секунд. PaymentURL
проверяется по точным HTTPS-хостам. Неизвестный формат/таймаут сохраняет
неопределённость; Message/Details не становятся пользовательской ошибкой или
записью журнала. Секреты и Receipt не отправляются клиенту.

Все новые HTTP bodies читаются через ограниченный stream. Chunked-запросы
без Content-Length реально проверены в HTTP. Support body рендерится обычным
React-текстом; нет unsafe HTML. API наследуют private/no-store и no-referrer
из Next headers. Страницы с cookie и Prisma динамические; финансовые/role
страницы не индексируются.

Аудит содержит тип команды, actor/entity/operation IDs, безопасные переходы и
счётчики; не содержит сообщения поддержки, Receipt, email, PAN/CVV, токены
или пароли. Финансовая история не удаляется для имитации успешного восстановления.

отдельным решением владельца от 10 ноября перенесён из критерия закрытия 06
