# Приёмка мониторинга и производительности

Пороги ниже предлагаются для первого staging прогона. Владелец утверждает их после измерения под ожидаемым профилем трафика. Зелёный локальный smoke подтверждает поведение проверок. Внешнюю доступность, нагрузочную ёмкость и доставку алертов измеряют на выделенном окружении с опубликованным каталогом и синтетическими аккаунтами. См. [план выпуска](RELEASE_PLAN_2026.md) и [порядок развёртывания](SELF_HOSTING.md).

## Внешний smoke и SSR

После публикации каталога оператор задаёт `POSTUPAI_STAGING_ORIGIN` с HTTPS доменом вида `staging.<свой домен>` и подтверждает запуск. Скрипт выполняет по одному анонимному GET на `/api/live`, `/api/ready` и `/`. Он проверяет значения `alive` и `ready` в JSON и закрытый вход на главную с `401` и Basic Auth. Учётные данные и cookies отсутствуют, редиректы не выполняются. `--rounds=10` даёт до 30 запросов за прогон, не более двух параллельно, с паузой между раундами. Таймаут каждого запроса 5 секунд. Вывод ограничен группой проверки, ожидаемыми/фактическими статусами, размерами и временем. Тела ответов и адрес окружения в него не попадают.

```bash
node scripts/staging-smoke.mjs --staging --confirm-owned-staging --rounds=10
```

Для внутреннего SSR прогона используйте выделенный стенд приложения и только loopback. На staging можно выполнить скрипт внутри контейнера web через `dc exec`. Доступ к origin по loopback минует сетевые характеристики HTTPS, поэтому внешний и внутренний замеры записывают раздельно. Запуск с `--ready` требует `200` на `/api/ready`. Без флага проверяется `503` с `not_ready` у локального snapshot preview.

```bash
node scripts/staging-smoke.mjs --local http://127.0.0.1:3100 --rounds=10
dc exec -T web node --input-type=module - --local http://127.0.0.1:3000 --ready --rounds=10 < scripts/staging-smoke.mjs
```

Loopback прогон также проверяет `200` и HTML у `/`, `/programs`, `/universities`. `firstMs` показывает первый ответ в этом прогоне. Для холодного замера заранее пересоздайте контейнер в закрытом staging и зафиксируйте время запуска. `p95HeadersMs` включает соединение и ожидание заголовков, `p95TotalMs` также чтение тела, `p95WarmHeadersMs` использует пробы после первого раунда. `maxDecodedBytes` измеряет распакованные байты, а предел скрипта в 2 MiB на HTML защищает прогон от чрезмерного ответа. Для проверки размера передачи включите отдельное измерение в браузере и запишите значение. Сравнивайте одинаковые commit, БД, число раундов, нагрузку, ширину экрана, политику кэша и сетевой профиль.

Небольшой smoke служит проверкой релиза. Перед публичным запуском отдельно согласуйте ожидаемые RPS и сценарии из плана выпуска, затем измерьте достаточное число запросов и отдельно проверьте холодный старт, телефон, клавиатуру, регистрацию, вход, поиск, публикацию каталога и трекер. Анонимный внешний прогон не авторизует запросы к личным данным и не проверяет пользовательские формы.

[Репетиция восстановления](BACKUP_RESTORE.md)                                  |

На стороне внешнего мониторинга нужны HTTPS пробники из независимой сети. Для 5xx и задержки требуется частный агрегирующий источник метрик прокси или провайдера. События приложения `SERVER_REQUEST_FAILURE` отражают захваченные исключения, а события worker `DEADLINE_WORKER_TICK` и `DEADLINE_WORKER_FAILURE` отражают циклы напоминаний. Эти потоки можно использовать для разбора причин. Полный счётчик HTTP берётся из агрегатора прокси. На приёмке согласуйте период хранения, доступ оператора, фильтры для auth/webhook ошибок и отдельный канал оповещения. Экспорт ограничьте числом событий, группой маршрутов, классом статуса и временем UTC.

## Приватный снимок состояния БД

HTTP-счётчики Caddy доступны внутри контейнера `edge` на `127.0.0.1:9180`.
Порт отсутствует в списке портов Compose. Оператор может посмотреть формат
выдачи командой `dc exec -T edge wget -qO- http://127.0.0.1:9180/metrics`.
Прокси публикует агрегаты по кодам, методам и обработчикам, включая гистограмму
длительности. Для непрерывного опроса настройте доверенный сборщик внутри
сетевого пространства edge. Назначьте получателя и выполните проверку алерта
на staging. [Метрики Caddy](https://caddyserver.com/docs/metrics).

Запускайте только через приватное подключение мониторинга с правами `SELECT` на указанные столбцы или в представлении с такими агрегатами. Используйте read-only транзакцию и лимиты. Бизнес-строки, адреса пользователей, IP, токены, тела писем, заметки, значения JSON-аудита и ссылки на оплату в метрики не попадают. Увеличение частоты опроса и полные пересчёты состояния очереди требуют повторной проверки стоимости запросов.

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '2s';
SET LOCAL lock_timeout = '250ms';

SELECT EXTRACT(EPOCH FROM ((CURRENT_TIMESTAMP AT TIME ZONE 'UTC') - (
  SELECT "finishedAt" FROM "WorkerHeartbeat" WHERE id = 'personal_deadlines'
)))::integer AS deadline_worker_age_seconds;

SELECT count(*) AS due_email_jobs,
       COALESCE(EXTRACT(EPOCH FROM ((CURRENT_TIMESTAMP AT TIME ZONE 'UTC') - min("availableAt")))::integer, 0)
         AS oldest_due_email_seconds
FROM "DeadlineEmailJob"
WHERE state = 'PENDING' AND "availableAt" <= CURRENT_TIMESTAMP AT TIME ZONE 'UTC';

SELECT count(*) AS expired_email_leases
FROM "DeadlineEmailJob"
WHERE state = 'SENDING' AND "leaseUntil" <= CURRENT_TIMESTAMP AT TIME ZONE 'UTC';

SELECT state, count(*) AS email_jobs
FROM "DeadlineEmailJob"
WHERE state IN ('FAILED', 'UNKNOWN')
GROUP BY state;

SELECT count(*) AS payment_reviews FROM "Payment" WHERE "needsReview";

SELECT count(*) AS expired_payment_leases
FROM "PaymentOperation"
WHERE state = 'IN_FLIGHT' AND "leaseUntil" <= CURRENT_TIMESTAMP AT TIME ZONE 'UTC';

SELECT count(*) AS pending_catalog_reviews
FROM "CatalogRevision" WHERE status = 'REVIEW';

COMMIT;
```

`NULL` у heartbeat означает, что worker ещё не записал успешный цикл. Отрицательный возраст требует сверки времени приложения и БД. Очередь писем может быть пуста при выключенной доставке или без согласия пользователя. Сравните счётчики с журналом worker. Для статуса можно выполнить `dc --profile reminders run --rm --no-deps worker node --import tsx scripts/deadline-worker.ts --status`. Отдельно проверьте письмо на согласованном синтетическом получателе и пройдите штатный сценарий с отказом SMTP.

## Проверка алерта и отката на staging

1. Согласуйте с оператором окно проверки, получателя и пороги. Сохраните базовые `200/200` live/ready, свежий heartbeat, digest образов, опубликованную ревизию и запись об используемой точке восстановления. Счётчики ошибок и очередь должны иметь начальные значения.
2. Остановите disposable web staging на время проверки или изолируйте его от тестовой БД в заранее согласованном окне. При остановке web ожидается потеря обоих пробников. При изоляции БД процесс остаётся жив, readiness отдаёт `503`. Дождитесь события мониторинга и подтверждения получателем. Отдельно остановите staging worker и дождитесь алерта по heartbeat. Следите, чтобы операторская почта и пути оповещения указывали на тестовых получателей.
3. Восстановите staging. Запишите UTC начала сбоя, первого сигнала, получения, подтверждения и восстановления. Проверьте отсутствие повторных писем у уже завершённых задач. Зафиксируйте случай без оповещения, если система не доставила сигнал в окно. Журнал содержит только времена, класс сбоя, среду, исход и имя ответственного.
4. Отработайте возврат на предыдущий digest при совместимой схеме и отдельное восстановление из резервной копии при несовместимой. Закройте edge на время переключения, проверьте отсутствие необъяснимых изменений `PUBLISHED`, миграций, проверочных данных трекера и сверки платежей. После возврата пройдите внешний smoke, приватный SSR, вход с синтетическим аккаунтом, heartbeat и восстановительный сигнал. Сохраните результат и время отката. [Инструкция переключения](SELF_HOSTING.md) · [Репетиция восстановления](BACKUP_RESTORE.md).

Подтверждение публичного запуска включает внешние DNS/HTTPS, алерт с подтверждением получателя, почту и приемлемые замеры нагрузки, RPO/RTO, независимую проверку безопасности, юридическую приёмку и банковский гейт. Результаты привязываются к конкретной среде, commit и дате. [План выпуска](RELEASE_PLAN_2026.md) · [Банковская приёмка](https://github.com/tonblognet/STUDY/issues/10).
