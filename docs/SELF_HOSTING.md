# Развёртывание на Linux с Docker Compose

Профиль слоя 07 рассчитан на отдельные серверы для staging и production. В каждом окружении Caddy принимает HTTPS, Next.js работает на внутреннем порту 3000, а PostgreSQL и SMTP предоставляются отдельно. Стандартный профиль занимает порты 80 и 443 на хосте. Размещение обоих окружений на одном сервере потребует отдельных адресов привязки или отдельного внешнего прокси. Для staging нужны синтетические данные и отдельные учётные записи. Актуальные ресурсы и условия запуска перечислены в [чеклисте владельца](OWNER_SETUP_CHECKLIST.md).

`deploy/compose.yaml` требует Docker Compose 2.30 или новее для `env_file.format: raw`. Подготовьте Docker-образы `runner`, `migrate` и `worker` из одного проверенного commit и запишите их адреса с `@sha256:…`. Для Caddy используйте проверенный официальный образ с digest. Конфигурация проверена на Caddy 2.11.9. Файлы `deploy/examples/*.env.example` содержат только шаблоны. См. [спецификацию Docker Compose](https://docs.docker.com/reference/compose-file/services/#format) и [автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).

Workflow `Release images` запускается вручную от `main` после успешного CI этого коммита. Он собирает три образа для Linux amd64 и выводит готовые строки с digest в отчёте GitHub Actions. Перед первым запуском настройте окружение `release-images` и доступ к GHCR. Для закрытых пакетов выдайте серверу доступ на чтение через защищённое хранилище. Workflow публикует образы в реестр, а перенос трафика оператор выполняет отдельно по инструкции ниже.

Для staging до merge выберите проверенный head PR. Из этого commit соберите
те же три target и опубликуйте их в выделенный закрытый реестр под тегом SHA.
Для каждой сборки запишите `containerimage.digest` из `--metadata-file` и
перенесите ссылки `image@sha256:…` в staging `release.env`. Этот путь нужен
для приёмки PR до выпуска образов от `main`.

Перед переключением production повторите миграцию, smoke web и проверку
worker на staging с точными digest из итогового отчёта `Release images`.
В production перенесите этот же набор ссылок. CI проверяет отдельные сборки
тех же исходников, а повтор на staging подтверждает опубликованные артефакты.

## Подготовка окружения

1. Выберите отдельные DNS-имя, Compose project и PostgreSQL для каждого окружения. В `POSTUPAI_DOMAIN` используйте одно DNS-имя в ASCII, без схемы, порта и пути. A/AAAA должны вести на соответствующий сервер. Разрешите входящие TCP 80 и 443 для HTTPS и ACME, ограничьте SSH доверенными операторами и DB доступом от сервера. Приложение, worker и команды обслуживания портов на хосте не публикуют. Развёртывание предполагает, что Caddy напрямую принимает клиентский трафик. Его правила доверия к IP нужно отдельно проверить при добавлении CDN или внешнего балансировщика.
2. Создайте вне репозитория каталоги `/etc/postupai/staging` и `/etc/postupai/production` с правами `0700` и файлы с правами `0600`. Держите доступ Docker только у уполномоченных операторов. Docker позволяет им читать окружение контейнеров, поэтому права на файлы дополняют ограничения доступа к daemon.
3. Скопируйте шаблоны в каталог окружения, убрав `.example`, и заполните их через защищённое хранилище или локальный редактор на сервере. В `release.env` находятся домен, режим, digest образов, флаги и путь к файлам. В остальных файлах используйте строки `KEY=value` без окружающих кавычек. Сырой формат сохраняет `$` в хеше и значения с пробелами. Зарезервированные символы в логине и пароле URL кодируются процентной записью. В shell не должно быть одноимённых переменных, которые переопределят манифест.
4. Сгенерируйте длинный случайный пароль предварительного доступа и выполните `caddy hash-password` интерактивно на защищённом компьютере. В `edge.env` сохраните только полученный bcrypt-хеш, пароль передайте сотрудникам защищённым способом. Пользователь Caddy называется `operator`. В самом приложении сотрудники входят в свои аккаунты. Caddy удаляет свой заголовок Basic Auth перед передачей запроса.
5. В `web.env` установите независимый случайный `AUTH_SECRET` от 32 символов и настройте SMTP с утверждённым `EMAIL_FROM`. Передавайте только права runtime. `worker.env` использует отдельный DB login, собственный доступ к SMTP и `DEADLINE_EMAIL_ENABLED=false` до проверки доставки. `migrate.env` доступен одноразовой команде миграции. `operator.env` доступен одноразовым командам подготовки первого сотрудника и черновика каталога. Значения `DATABASE_URL` четырёх сервисов различаются. Параметры `APP_URL`, `DEPLOYMENT_MODE` и `CATALOG_STORAGE` задаёт Compose.

Для PostgreSQL 16 используйте отдельного владельца прикладной схемы для миграций и непривилегированные DB logins для web, worker и operator. Web требуется `SELECT` на `_prisma_migrations` для readiness, а также права runtime на прикладные таблицы. Worker нужны чтение пользователя, трекера, настроек и каталога, запись уведомлений и операции над очередью/heartbeat. Operator нужны только права для явно выполняемых команд. Для запросов `SELECT … FOR UPDATE` PostgreSQL также требует право `UPDATE` хотя бы на один столбец таблицы. Сверьте права на staging с текущими Prisma моделями и SQL запросами и проверьте, что web не может менять историю миграций или создавать таблицы.

В Prisma URL для облачной БД укажите `sslmode=require&sslaccept=strict`, проверенное DNS-имя и ограниченный `connection_limit` с учётом суммы пулов всех сервисов. Если провайдер использует отдельный CA, добавьте защищённый монтируемый сертификат и укажите его путь по документации провайдера и Prisma. Требуемые проверки TLS и реальное соединение выполните на staging. [Параметры PostgreSQL в Prisma 6](https://www.prisma.io/docs/orm/v6/overview/databases/postgresql#arguments).

## Первый закрытый запуск

Команды выполняет уполномоченный оператор на Linux с отдельным манифестом окружения. Сначала используйте staging. Для production до прохождения условий выпуска держите `POSTUPAI_PUBLIC_TRAFFIC=false`. Staging остаётся закрытым независимо от этого флага.

```bash
set -euo pipefail
RELEASE_ENV=/etc/postupai/staging/release.env
dc() { docker compose --env-file "$RELEASE_ENV" -f deploy/compose.yaml "$@"; }

dc --profile maintenance --profile reminders config --quiet
dc --profile maintenance --profile reminders config --images |
  awk '!/@sha256:[0-9a-f]+$/ || length(substr($0, index($0, "@sha256:") + 8)) != 64 { bad=1 } END { exit(NR == 0 || bad) }'
dc --profile maintenance --profile reminders pull
dc run --rm --no-deps edge caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
dc run --rm --no-deps migrate
dc up -d --wait --wait-timeout 120 web edge
```

`config --quiet` проверяет конфигурацию без вывода значений. Полный вывод `docker compose config` и `docker inspect` может раскрывать секреты. После миграций при необходимости примените предусмотренные права на новые таблицы. Профиль `maintenance` используется для просмотра конфигурации и загрузки образов, а миграция выполняется одноразовой командой `run`.

Проверьте DNS, сертификат и HTTP → HTTPS. Caddy пропускает публичные проверки `GET` и `HEAD` на `/api/live` и `/api/ready`, которые возвращают краткий статус, и запрашивает пароль на остальных страницах. `/api/live` ожидает `200`. На пустой БД `/api/ready` ожидает `503` до первой публикации. В закрытом режиме оператор может открыть регистрацию, подтвердить собственную почту и пройти процедуру первого `SUPERADMIN`.

```bash
# Используйте ID согласованного подтверждённого аккаунта.
read -r -p 'ID аккаунта: ' BOOTSTRAP_USER_ID
export BOOTSTRAP_USER_ID
dc run --rm --no-deps --env BOOTSTRAP_USER_ID operator \
  node --import tsx scripts/bootstrap-staff.ts --apply
unset BOOTSTRAP_USER_ID

dc run --rm --no-deps operator node --import tsx scripts/data-pipeline.ts import --dry-run
# EDITOR_EMAIL задаёт оператор по адресу согласованного редактора.
dc run --rm --no-deps operator node --import tsx scripts/data-pipeline.ts import --actor="$EDITOR_EMAIL"
```

Войдите в приложение, примите редакционный черновик через `/admin/catalog` и проверьте совпадение версии в `/api/programs`. Для последующих импортов используйте точную исходную ревизию. После публикации `/api/ready` должен вернуть `200`. [Публикация каталога](CATALOG_PUBLICATION.md).

Запустите worker после миграций и выдачи прав. Проверьте heartbeat и выполнение задач на синтетическом трекере. После приёмки почты установите `DEADLINE_EMAIL_ENABLED=true` в `web.env` и `worker.env`, затем пересоздайте оба сервиса. Web показывает отдельное согласие пользователя, worker отправляет только при сохранённом согласии и подтверждённой почте. Для экстренной паузы выключите флаг в обоих файлах и пересоздайте сервисы. Фактическую доставку, повторы и алерт проверьте на staging.

```bash
dc --profile reminders up -d worker
dc exec worker node --import tsx scripts/deadline-worker.ts --status
```

Для реальной банковской приёмки на отдельном staging включите `POSTUPAI_ACCEPT_BANK_WEBHOOK=true` и пересоздайте edge. Через внешнюю сеть станет доступен только `POST /api/webhooks/payments` без предварительного пароля, а приложение продолжит проверять банковскую подпись. Зафиксируйте результат и верните значение `false`, если входящие уведомления больше не нужны. Приёмку и условие оплаты ведём в [issue #10](https://github.com/tonblognet/STUDY/issues/10).

## Открытие трафика, смена версии и откат

1. Перед выпуском сохраните текущий манифест с digest образов и подготовьте проверенную точку восстановления PostgreSQL. На staging отрепетируйте миграции, смену образов и откат на копии схемы. Подтвердите совместимость старого приложения с новой схемой для отката без восстановления данных.
2. На production сохраняйте закрытый режим в течение подготовки. Перед выпуском подтвердите соответствие сертификата домену, редакционную публикацию, readiness `200`, регистрацию/вход с реальными письмами, heartbeat и работоспособность внешнего мониторинга. Условия банковской, юридической и внешней проверки безопасности перечислены в [плане выпуска](RELEASE_PLAN_2026.md).
3. После согласования запуска установите `POSTUPAI_MODE=production` и `POSTUPAI_PUBLIC_TRAFFIC=true` в production манифесте. При смене режима с staging пересоздайте и web, чтобы `DEPLOYMENT_MODE` совпадал, затем повторно проверьте readiness. Если режим уже production, пересоздайте только `edge`. Публичный маршрут Caddy проверяет `/api/ready` каждые 10 секунд и выдаёт `503` при отсутствии готового upstream. Между пробами возможна задержка обнаружения сбоя. Точка принятия решения перед включением остаётся внешней проверкой `200`, а Docker healthcheck следит за живым процессом.
4. При неудачной выкладке сначала отключите публичный трафик. Если старая версия совместима с уже применённой схемой, верните прежний набор digest и пересоздайте web, edge и worker. При несовместимой схеме оставьте трафик закрытым, остановите worker и восстановите в отдельную БД из проверенной точки. Проверьте целостность, версию каталога, вход и незавершённые платежи, прежде чем переключать трафик. Команда `migrate deploy` не используется для обратного применения SQL.

```bash
# После изменения флагов edge перечитывает их при пересоздании контейнера.
dc up -d --no-deps --force-recreate edge
```

Для работающей платёжной интеграции планируйте приём подписанных уведомлений во время обслуживания или согласуйте паузу с провайдером. Публичный маршрут не повторяет запросы при ошибках upstream. Встроенный access log Caddy выключен, а журнал сырых HTTP ошибок исключён. Подключение коллектора, который сохраняет URL, query, заголовки или тело запроса, требует отдельной проверки. Docker ограничивает размер локальных журналов каждого сервиса.

## Как проверять этот профиль

10 ноября 2026 Compose 5.7.0 разрешил модель со стандартным набором сервисов и обоими дополнительными профилями на синтетической конфигурации. Caddy 2.11.9 прошёл проверку конфигурации и loopback HTTPS smoke с тестовым CA. Проверены закрытый и открытый режимы, методы проверок и банковского маршрута, подмена входящих forwarding-заголовков, удаление Basic Auth перед upstream, HSTS, `no-store`, отклонение слишком большого запроса и ответ `503` после потери readiness. Docker-сеть, публичный ACME и доставка на выделенном окружении требуют следующих прогонов.

- Локально или в CI используйте вымышленные `*.env`, изолированную сеть и тестовую БД. Проверьте `config --quiet` с обоими профилями, `config --images`, затем `caddy validate` на том же digest, который указан в манифесте. Убедитесь, что хостовые порты есть только у edge и секрет каждой роли доступен только её сервису. Для проверки модели используйте только синтетический вывод конфигурации.
- На Linux выполните smoke с реальными Docker-образами, включая чтение статики при `read_only`, миграции и старт контейнеров с указанными пользователями. Проверьте `/api/live`, закрытую страницу, `/api/ready` до и после публикации и реакцию на остановку тестовой БД. Проверьте, что входящий `X-Forwarded-For` заменён значением от Caddy.
- На staging запишите digest, версию каталога, результаты HTTPS и отзыва сессий, время восстановления, успешный SMTP и доставку алерта. В журнале выпуска укажите ответственного и проверенную схему отката. Это отдельный этап с реальными ресурсами из чеклиста владельца.
